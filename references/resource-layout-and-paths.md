## 目录模型

推荐结构：

```text
entry/src/main/
├── config.json
├── js/<Ability>/
│   ├── app.js
│   ├── pages/<page>/<page>.hml|.css|.js
│   └── common/                    # 可选，创建项目时通常不存在，开发者自行创建
│       ├── img/
│       │   └── icon.png
│       ├── utils.js
│       └── style.css
└── resources/
    └── rawfile/                   # 需要 @system.file 访问的原始文件
        ├── data.json
        └── audio/
```

开发文档说明 `common` 属于可选目录，并明确公共媒体、JS 和样式可放在其中。不要因为新工程没有 `common` 就把页面图片随意放到 `pages`、`resources/base/media` 或生成目录；需要页面直接引用资源时主动创建 `js/<Ability>/common`。

## common 私有公共资源

`common` 的“公共”是指同一应用/Ability 内多个页面共享，不是用户文件系统中的公共目录。打包后它属于应用私有资源命名空间，用户在真机文件目录中看不到，只有应用自身通过资源路径使用。

- 页面图片、动画帧和 CSS 背景图放在 `entry/src/main/js/<Ability>/common/` 或其子目录。
- HML 和 JS 数据中的媒体路径使用绝对资源路径，例如 `/common/img/icon.png`。
- CSS 使用 `url(/common/img/icon.png)`；带引号也可，但保持项目内一致。
- 公共 JS 代码放在 `common`，从页面使用相对路径导入，例如 `../../common/utils.js`。不要用 `/common/utils.js` 作为代码导入路径。
- 公共样式按相对路径 `@import '../../common/style.css'`。
- 当被导入的 JS 与调用代码不在同一目录时，被导入 JS 内部引用媒体必须使用 `/common/...` 绝对路径，因为 webpack 打包会改变代码目录。
- 图片文件名必须使用英文 ASCII，否则 Lite Wearable 可能无法识别或读取。硬性格式使用 `^[A-Za-z0-9][A-Za-z0-9_-]*\.(png|jpg|jpeg|bmp|gif|webp)$`；推荐全小写，例如 `enemy_01.png`。
- `common`、`rawfile` 内图片路径的子目录也只使用英文字母、数字、`_`、`-`。项目所在的 Windows 上级目录可以是中文，不受此规则影响。
- 文件名、目录名和引用路径大小写完全一致。禁止中文、空格、全角符号、emoji 和其他非 ASCII 图片名称；重命名时同步修改所有 HML、CSS、JS 和配置引用。

固定资源示例：

```html
<image src="/common/img/icon.png" class="icon"></image>
```

```javascript
import utils from '../../common/utils.js';
```

`common` 适合应用自带、只读、可被 HML/CSS 直接渲染的固定资源。不要试图用 `@system.file` 枚举或读写 `/common/...`，也不要把它当作用户可见文件路径。

## rawfile 真机文件资源

`resources/rawfile` 用于需要以文件方式读取的原始数据、音频或其他资源。按社区真机经验，打包后它会出现在真机侧应用可访问目录，通过以下 URI 使用：

```text
源码: entry/src/main/resources/rawfile/data.json
真机只读 URI: internal://app/rawfile/data.json
```

- 使用 `@system.file` 的 `readText`、`list`、`access`、`copy` 等接口访问。
- rawfile 打包区按只读资源处理；需要修改时先复制到 `internal://app/` 下的可写位置。
- 音频继续遵守 `audio-on-lite-wearable.md`：从 rawfile 复制后再交给 `@system.audio` 播放。
- 图片只有在业务明确需要文件接口路径时才放 rawfile。此类图片不能以 `/common/...` 方式假装成普通页面资源，必须按真实 URI/复制流程实现并在真机验证渲染。
- 不把电脑端 Node 工具、源素材、未使用文件或秘密信息放入 rawfile；它们会进入安装包和真机侧资源目录。

## 选择规则

| 需求 | 目录 | 访问方式 |
|---|---|---|
| HML/CSS 直接显示的应用内固定图片 | `js/<Ability>/common` | `/common/...` |
| 页面共享 JS | `js/<Ability>/common` | 相对 `import` |
| 页面共享 CSS | `js/<Ability>/common` | 相对 `@import` |
| 需要 `@system.file` 读取/枚举的 JSON、文本、二进制 | `resources/rawfile` | `internal://app/rawfile/...` |
| 需要播放的打包音频 | `resources/rawfile/audio` | 首次复制到 `internal://app/...` 后播放 |
| 应用图标等系统资源 | `resources/base/media` | 仅按配置/系统资源规则，不替代页面 `/common` 图片 |
| 运行时生成或用户修改的数据 | `internal://app/` 可写目录 | `@system.file`，不要写回 rawfile/common |

## 验证要求

按已知实际环境约束处理：部分 DevEco Studio 5.0/API 10 预览器和 Lite Wearable 模拟器不能调用 `@system.file`。因此：

1. `/common/...` 固定资源可先用构建和预览检查路径，但仍要在目标分辨率真机确认显示与图片池。
2. 任何 `internal://app/rawfile/...`、`@system.file`、rawfile 图片或复制流程都必须打包、签名并安装到真机测试。
3. 预览器/模拟器报 file 接口不可用时，不能据此改掉正确的真机实现；记录为环境限制。
4. 预览器/模拟器能够显示界面，也不能写成“rawfile 已验证”。发布结论必须明确列出真机读取、复制、路径、格式和异常恢复结果。
5. 审计 `/common/...` 静态路径是否存在；包含 `{{...}}` 的动态路径无法完全静态解析，必须遍历所有运行时组合并真机验证。
6. 审计所有打包图片的英文 ASCII 文件名和资源子目录；任一非法名称都属于发布阻塞项，不能以 Windows 或预览器偶尔能显示为放行依据。

此处“部分 DevEco Studio 5.0/API 10 预览器与模拟器不支持 file 接口”来自社区真机开发经验，应作为对应目标工具链的硬验证限制；若换用其他 SDK/模拟器版本，重新实测后再更新结论。

## 包内文件数预算（比体积更容易翻车）

**真机拒收的头号变量是「安装包包内文件数 / 单目录条目数」，不是 HAP 体积。**
实测样本（见 `G:/arknights/SIGNING.md`）：被拒收的包内层 886 个文件（`rawfile` 429 条目录 + 头像 430 个）；同批**能装**的参考包最多 **157 个文件**、**单目录 ≤72**，且**完全没有 rawfile**。体积 8.6MB 的词典能装，3.6MB 但 886 文件的包被拒。

### 图片无法合并成图集

Lite 的 `image` 组件**只有 `src` 一个属性**，SDK 引擎二进制里搜不到 `background-position` / `background-image` / `sprite` / `clip` / `object-fit` 任何字样 —— **没有图集裁剪能力，一张图只能整张显示**。
所以「N 个物品各自一张图标」= **N 个文件**，无法用 sprite 合并降文件数。

### 三条可用的降文件数手段

| 手段 | 效果 | 代价 |
|---|---|---|
| **每目录分片** | 把图标按 `common/img/<name>/<i//60>/<i>.png` 分目录，单目录 ≤60 | 不减少总数，只压单目录条目数 |
| **减少图标条数** | 只给「每品类 Top N」真图标，其余共用**一张**占位图（`common/img/x/_ph.png`），运行时用 `ord < 图标数` 判断走占位 | 长尾物品无图 |
| **占位图 + 品质色块** | 全部走一张占位图，靠 `background-color` 表达稀有度 | 视觉最弱，但文件数最少 |

### 实测口径（1094 件物品工程）

| 方案 | 图标文件 | 包内条目 | lite 包体积 |
|---|---:|---:|---:|
| 全量图标 | 1094 | **1144** | 9.29 MB |
| 每品类 Top24 | 120 | **170** | 1.45 MB |
| 全占位 | 0（共用 1 张） | **50** | 449 KB |

> 图标源图缩到 40×40 RGBA，构建期由 ace-loader 转成 `.bin`（**RGBA 裸像素 = w×h×4**，不压缩，所以体积与源 PNG 大小无关，只与边长和**张数**有关）。

### 落地建议

1. 生成图标的脚本要提供 `--icons full|topN|none` 三档开关，**同时出 2~3 个对照包**，先发最小档验证安装，再逐步加码 —— 文件数红线没有官方数值，只能实测。
2. 数据（JSON）尽量合并成**少量分片**放 rawfile，用链式 `next` 顺序读取；几百条记录只占十几个文件。
3. 出包后**必须数一遍包内条目数**（解 zip 中央目录 / 解 lite 内层 `.bin`），不要只看 HAP 体积。

## 数据不要靠运行期读 rawfile（真机实测不可靠）

**真机反馈：「无法读取文件」** —— `@system.file` 读 `internal://app/rawfile/...` 失败，
`readText` 的 success 回调不触发 / 走 fail，页面停在错误态，游戏直接玩不了。

> 这与 `file-and-storage-on-lite-wearable.md` 里「预览器/模拟器不支持 file 接口」是两回事：
> 这次是**真机**也读不出来。**物品表、配置表这类只读数据，一律编译期内联成 JS 模块。**

### 内联会立刻撞上单页 48KB 上限

ace-loader 把公共模块**静态内联进每个引用它的页面**。一份数据表被 M 个页面 import = 页面里 M 份副本。

实测：459 条中文记录 ≈ **16.5KB**（其中名称字段占 46.7%），全量内联后
**pack 页从 36.9KB 涨到 53KB —— 直接爆 48KB**。

### 分配策略：按「页面真实需要什么」切模块

| 数据 | 放哪 | 谁引 |
|---|---|---|
| 跨页会话（大对象的搬运工） | `session.js`（<1KB） | 所有页 |
| 公共配置（品类 / 配色 / 权重 / 箱型基本属性） | `config.js` | 需要配置的页 |
| **只被某一页用的重配置**（箱型掩码、评级阈值…） | `packcfg.js` | **只有那一页** |
| **全量表**（含名称等长文本） | `db.js` | **只有真正列出全量的页** |
| 数据访问 + 业务算法 | `data.js` | 用到表的页 |

两条关键做法：

1. **流程页不要背全量表**。抽卡 / 选择时把「选中项 + 展示所需字段」构造成轻对象塞进会话
   （例：`{ord,nm,q,w,h,pr,vp,img}`），后续页面从会话读 —— 于是 `pack` / `result` 这类页
   **完全不 import 全量表**，产物从 36.9KB 掉到 30.5KB。
2. **重配置按页拆**。把 mask、阈值这类只被一个页面用的常量单独成文件，别塞进公共 config
   —— 实测能省 ~0.6KB，而正是这 0.6KB 决定了某一页超不超限。

### 换档位 / 换数据后必须重新生成

「哪些条目有真图标」这类信息也随数据一起内联了 → **换图标档位后必须重跑数据生成脚本**，
否则运行时判断与实际资源不一致（表现为全部走占位图，且不报错）。

### 删掉运行期 IO 的连带收益

数据内联后 `core.js` 可以彻底去掉 `import file from '@system.file'` 与 `readText`/`hasReadText`：
既省 ~450B（所有页面受益），也让工程**完全不依赖 file 模块**；同时 `resources/rawfile/`
可以整个移出工程，**包内条目再减 10**。

### 合页会把单页 48KB 顶爆 —— 先按页面切数据，再谈 UI 合并

想把「选容器 → 抽卡 → 装填」合并成一个页面时实测：产物从 38KB 涨到 **53997 B**，超 49152 上限 4.8KB。
根因不是 UI 变复杂，而是**合并后那个页面同时背上了 `db.js`（459 条 ≈17KB）+ `packalg.js` + 装填逻辑**。

**判定准则**：页面的体积 ≈ `core + 它直接/间接 import 的所有数据模块 + 模板 + 逻辑`。
只要一个页面同时需要「全量表」和「重算法」，就必然逼近红线。
→ **保持"抽卡页只抽卡、装填页只装填"的拆分**：抽卡页把候选详情（轻对象）塞进会话，
装填页从会话读、**完全不 import 全量表**。拆完是 38382 + 25818，两边都很宽裕。

## 官方素材的获取姿势（无接口时怎么找）

很多游戏官网只给「新闻稿 + 图片 CDN」，**没有结构化图鉴接口**。可复用的三步：

1. **抓已上线的第三方数据页**，从 DOM 里读出图片真实 URL，找出 CDN 的**命名规律**
   （例：`playerhub.df.qq.com/playerhub/60004/object/<objectId>.png`）。
2. **分析 objectId 的前缀分布**（已抓到的资源按前缀分组统计），定位「资源集」分段。
3. **区间探测**：写脚本并发遍历某前缀下的连续 ID，把命中的图**拼成一张预览大图**一眼扫完
   （`tools/probe_cdn_ids.py` 就是这个思路）。

> ⚠️ 区间探测只能**证伪**，不能保证覆盖。实测某集在 `150800xxxxx` 段命中 212 张，
> 但相邻的 `1508006/1508007/1508010` 段**全 0 命中** —— 说明资源集并不按前缀连续延伸。
> 找不到目标资源时，**如实记录缺口并降级为占位**，比硬凑错误素材强。
